用一句話讓 opencode 做完一個專案

從需求到上線，只靠對話

我想分享的不是「做出什麼功能」，而是「我是怎麼問的」

這場對話的數字

項目 數字
opencode session 5 個
我輸入的 prompt 59 次
開發時間 2 天（8/8 – 8/9）
產出提交 7 次
開編輯器次數 0
伺服器成本 NT$0

開場的第一個 prompt

「我想開發一個定時查詢機票價格並發送通知的自動化腳本。請幫我設計並開發這個專案，要求如下： 程式語言：使用 Python（或 Node.js）。 機票查詢：透過爬蟲或 Skyscanner / Google Flights API / Amadeus API 查詢指定航線與日期的機票價格。 通知機制：當價格低於設定的目標價（例如 NT$ 15,000）時，透過 Line Notify / Telegram Bot / Email 發送通知。 定時執行：撰寫一個排程設定…讓它每天自動執行二次。 請先在 Plan 模式 下規劃專案結構與步驟，列出需要的第三方套件，待我確認後再開始建立檔案與撰寫程式碼。」

這個 prompt 為什麼有效

我給的 效果
一句話主旨 讓 AI 知道目標，不被細節淹沒
4 個明確維度（語言／查價／通知／排程） 把模糊需求變成可驗收的規格
列出 2–3 個候選方案 讓 AI 做比較，而不是猜
指定 Plan 模式 拿到「方案比較」而非直接產生程式碼
「待我確認後再開始」 保留人類的決策節點

這 5 行決定了整個協作模式：人負責定義與決策，AI 負責展開與執行。

關鍵在最後一句：先 Plan 再 Build

Plan 模式回報了什麼：

  • 選型比較（為什麼用 google-flights-search 而不是官方 API）
  • 完整檔案結構（main.py + tracker/ 模組化切分）
  • 第三方套件清單
  • 已知風險（爬蟲非官方介面、可能查無結果）

然後我只需要 11 個字：

「請開始執行 Build」

切換模式＝按 Tab。從此進入「提需求 → 交付 → 驗收」的節奏。

第一次上線就有模有樣

AI 產出的成果：

  • main.py + tracker/{config,search,notify,history}.py 模組化結構
  • 設定檔 config.yaml（YAML 分層）與 .env.example 範本
  • cron: 0 1,13 * * * → 台灣時間 09:00 / 21:00 每天自動跑兩次
  • 手動可觸發的 workflow（workflow_dispatch）

我在這個階段做的事：開 GitHub repo、設定 3 個 Actions Secrets、手動觸發測試。

第一次部署的插曲（報錯型提問）

上線後我開始問「看不懂的現象」：

「中間有出現一個 warning 有需要注意什麼嗎 Node.js 20 is deprecated.」

「上面的 status 是 success，但中間的 check-price 還在一直轉圈圈，這樣是有成功嗎 ?」

「data/history.csv 在哪裡 ?」

觀察重點：我不會直接說「壞了」，而是描述我看到的畫面 — 轉圈圈、deprecated、檔案不見。 AI 因此能精準定位，而不是猜錯方向。

需求演進：從固定設定到對話設定

第一版能跑之後，我開始問「能不能更好用」：

「如果想改成可以在 telegram 設定機票日期、起點、終點、單程或來回，有辦法做到嗎 ?」

這個問題把專案從「一個腳本」推向「一個服務」—— 設定不用再改檔案，用聊天就能調。

接下來 AI 幫我釐清了所有權限制（這些是文件查不到的）：

「這樣還需要 VPS 嗎 ?」

「有辦法執行 Github Action 時，透由讀取 Telegram user 的資訊，例如簡介之類的，得到想查詢的機票訊息，然後再依此去做搜尋嗎 ?」

關鍵轉折：先問價格，再決定要不要做

三句 prompt，決定了整個專案走哪條路：

「如果改用 line chatbot 有機會吗」

「LINE Push API 是免費的嗎?」

「那請幫我改成用 line 的方案」

我先問「成本」，再決定「要不要做」。 AI 回答免費額度後，我才確認轉向 — 這是人的判斷，不是 AI 的。

AI 接著幫我比對兩個平台的本質差異：

Telegram LINE
收訊機制 需要常駐程式（long polling） 只能 webhook
免費排程 雲端無狀態，程式會死 webhook 交給 GAS 即可

→ 結論：LINE 只能 webhook ⇒ 接收端選 Google Apps Script（免費、永遠在線、免維護）

最終架構

LINE 使用者 ──訊息──> LINE Messaging API ──webhook──> GAS 接收器
   ▲                                                   │ 對話式設定 /set
   │  Push API（約 60 則/月，免費額度內）              │ 寫入 GitHub Gist
   │                                                   ▼
   └──── GitHub Actions（每日 09:00/21:00）── curl 下載最新設定
                                                     │
                                          查 Google Flights → 低於目標價才通知

設定存放於公開 Gist（不污染 repo），Actions 每次執行用 curl 拉最新版。

上線實戰：踩坑地圖

2 天內撞上 7 個坑，全部在對話中解決：

# 問題 解法
1 不知 Gist 是什麼 請 AI 給逐步圖文
2 GAS 授權失敗 改用無權限範圍的部署方式
3 PAT 不知選哪個 只要 gist 權限
4 Expiration 選多久 先問建議再決定
5 LINE Verify 一直 302 加 doGet 暖機
6 Access to this API is not available 平台硬限制，改用 webhook 註冊
7 TWD 237 卻是 7641 強制注入 curr=TWD

接下來挑 3 個最有代表性的 細說。

坑 1：LINE Verify 一直回 302（最卡的一題）

症狀（我把錯誤整段貼回去）：

「Step 5：串接 LINE Webhook… Verify 出現以下 error The webhook returned an HTTP status code other than 200. (302 Found)」

排查過程（每一句都是真實 prompt）：

「3. 先「暖機」一次… 出現 找不到以下指令碼函式：doGet」

「加了 doGet 後，用瀏覽器可以得到 OK Webhook URL」

「按 Verify（驗證）還是出現 error (302 Found)」

「步驟 1 的無痕測試 顯示 OK」 → 「測試 B 有回應」

解法：GAS 的 ContentService 會 302 轉址，LINE 的 Verify 要求 200。實際投遞是成功的，這是已知限制。

坑 2：TWD 237 卻是 7641（最典型的 bug）

症狀：

「已經完成 Step 8／Step 9 也有收到通知，但訊息顯示 TWD 237 但實際點開頁面是 7641 ，似乎是美金跟台幣換算的問題」

AI 的診斷：不是換算錯誤，是根本查到美金。 google-flights-search 只送 hl=zh-TW 不送幣別，Google 依伺服器 IP 地區決定幣別 → GitHub Actions 在美國 → 回美金。

修法（注入 curr 參數，兩處都要改）：

# tracker/search.py — 強制請求網址帶上幣別
base = _gf_fetcher._GF_SEARCH_URL
if "curr=" not in base:
    _gf_fetcher._GF_SEARCH_URL = f"{base}?curr=TWD"

驗收（重要：一定要回頭確認）：

「顯示幣別正常了，是台幣」

坑 3：Access to this API is not available

症狀：

「回傳的訊息是 {"message":"Access to this API is not available for your account"}」

我接著追問根因：

「有辦法看出 取得好友列表 為什麼不支援嗎 ? 如果將來想將這個功能分享給其他人，是不是可以透過取得好友列表得到要通知的名單 ?」

結論：這是平台的硬限制，不是設定錯誤 — 免費方案拿不到好友名單。 → 改用 webhook 事件中夾帶的 userId 當通知名單。

Lesson：問「為什麼」比問「怎麼辦」更有價值，因為它決定了是改程式還是改期待。

59 次 prompt 的 4 種型態

型態 目的 真實例子
規格型 一次講清需求 「我想開發一個定時查詢機票價格…要求如下…」
追問型 釐清不確定處 「這樣還需要 VPS 嗎 ?」「Expiration 要選多久 ?」
報錯型 貼錯誤求診 「出現以下 error (302 Found)」「訊息顯示 TWD 237 但實際是 7641」
決策型 確認方向 「LINE Push API 是免費的嗎?」「那請幫我改成用 line 的方案」

實測統計：開發階段 46 次 prompt 中，完整的需求規格只講過 4 次，其餘 42 次都是追問、確認、報錯與決策。

→ 需求講一次就夠，真正的功夫在追問與除錯。

報錯怎麼問最有效

效果差：

「它壞了」

效果好的三要素：

「看到的畫面 + 原本預期 + 已試過什麼」

實例（照抄我當時的原句）：

「按 Verify（驗證）還是出現 error (302 Found)」

三要素齊備：畫面＝error 內容、預期＝Verify 成功、已試過＝加了 doGet、暖機、無痕測試。

AI 因此不用猜，能直接給排查步驟。

人機分工

交給 AI 的：

  • 架構設計與模組切分
  • 寫程式、除錯、補測試
  • 技術選型比較（並揭露文件沒寫的限制）
  • 產生文件（README、CHECKLIST、AGENTS.md）
  • 部署設定草擬與排查建議

人必須自己做的：

  • 決定要不要花錢、要不要轉向
  • 申請帳號（LINE 官方帳號、GAS、GitHub PAT）
  • 實際部署與設定 Secret
  • 驗收：「顯示幣別正常了」

開玩笑地說：整個過程我沒有寫過一行 code，但每一個技術決策都是我做的。

交付與交接：讓下一次的自己接得上

開發結束時，我還多問了三個問題：

「如果之後有修改這個專案的需求，該如何做 ? 可以把這個 session 存下來嗎 ?」

得到的答案：

做法 用途
AGENTS.md（commit 進 repo） 專案知識＋踩坑，opencode 自動讀取

重點回顧

  1. 第一次 prompt 就要寫得像規格書，並指定「先 Plan」
  2. Plan 模式拿比較，Build 模式拿產出，Tab 一鍵切換
  3. 先問成本再決定要不要做 — 商業判斷留給人
  4. 報錯時描述畫面，不要只說「壞了」
  5. 問「為什麼」勝過問「怎麼辦」，能分辨是程式問題還是平台限制
  6. 一定要回頭驗收：「顯示幣別正常了」
  7. 結束時寫 AGENTS.md，讓下一次的自己（與 AI）接得上
